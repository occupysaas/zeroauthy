# Translating zeroauthy

Hosted pages (login, signup, logout, errors) read their text from
`internal/i18n/locales/<language>.json`. English (`en.json`) is the
reference; any key a language does not translate falls back to English.

## Add a language

1. Copy `internal/i18n/locales/en.json` to `<tag>.json`, where `<tag>` is a
   BCP 47 tag in lowercase (`fr`, `pt-br`).
2. Translate the values. Keep every `${variable}` exactly as in English;
   you may move it within the sentence. Write your own wording — do not
   copy text from other products.
3. Run `go test ./internal/i18n/`. It fails on unknown keys or changed
   variables.
4. Tenants use the language by listing it in `enabled_locales`.

## Per-tenant wording

Operators override any key per tenant in the seed file:

```yaml
custom_text:
  login:            # prompt
    fr:             # language (must be in enabled_locales)
      login:        # screen
        title: "Connexion à ${companyName}"
```

`enabled_locales` entries must be BCP 47 tags in canonical form, such as
`en`, `fr-CA` or `pt-BR`. A non-canonical tag such as `en_US` or `fr-ca` is
rejected with the canonical spelling as a suggestion; `und`, private-use
(`x-…`) and grandfathered (`i-…`) tags are rejected.

Language keys are matched against `enabled_locales` case-insensitively
(`fr-ca` applies to `fr-CA`); two keys under one prompt that differ only by
case are rejected. Custom text for a language that is not in
`enabled_locales` is rejected.

Custom text applies to its exact language only: custom text for `fr` does
not apply to users whose page language is `fr-CA`. To cover them, either
enable `fr` alone (so `fr-CA` browsers get `fr`), or add custom text for
`fr-CA` as well.

Valid keys are the ones in `en.json`. An unknown key under the `zeroauthy`
prompt fails the seed, which catches typos. Unknown keys under Auth0's
prompts (`login`, `signup`, `reset-password`, …) are accepted and ignored:
they are documented Auth0 keys for screens zeroauthy does not render yet,
so configuration written for Auth0 still loads. They still need an enabled
language and non-empty text. Empty or whitespace-only text is rejected
for every key.

Setting Auth0's `signup.signup.password-policy-not-conformant` replaces
all three password policy messages (too short, too long, character
classes) for that language.

Available variables: `${companyName}` and `${clientName}` on any key, plus
the ones the English string for that key uses. Any other variable is
rejected.

Error pages shown after a verified login transaction keep that
transaction's language.

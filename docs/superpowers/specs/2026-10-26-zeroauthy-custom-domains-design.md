# zeroauthy — Plan 23 design: custom domains and automatic certificates

- **Status:** Proposed design; implementation is not authorized by this document. Local choices below are the author's recommendations, not observations of Auth0 or prior maintainer decisions.
- **Date / baseline:** 2026-10-26; `1b6ffef` includes completed Plan 22.
- **Roadmap:** [Plan 23](2026-10-19-zeroauthy-management-roadmap-design.md#plan-23--custom-domains-with-automatic-certificates-full-design).
- **Implementation plan:** [Plan 23 tasks](../plans/2026-10-26-zeroauthy-plan-23-custom-domains.md).
- **Policy:** [CLEAN_ROOM.md](../../../CLEAN_ROOM.md). Public documentation, standards and licensed SDK/tool sources only; a separate authorized observer must supply any live upstream evidence.

## 1. Outcome, scope and baseline

An operator adds `login.customer.example`, proves control, and gets a working branded authentication origin. Zeroauthy either obtains and renews that origin's certificate or authenticates a customer-operated TLS proxy. Multiple instances share ownership, challenges, certificates and renewal work. Operators can designate a default domain for Management API-generated user links. Hosting operators can additionally provision one DNS-01 wildcard for tenants beneath `base_domain`, using DigitalOcean DNS first.

These are related deliverables with separate task/test boundaries: the domain registry and API work with existing TLS termination; managed issuance builds on that registry; hosted wildcard issuance reuses the same coordinator. Complete Plan 23 includes all three. No tenant-supplied DNS-provider credentials, arbitrary DNS plugins, uploaded TLS private keys, CDN provisioning, wildcard customer domains, automatic redirects between login domains, shared cross-domain SSO cookies, organization branding, passkey execution or ACUL. Domain `relying_party_identifier` is validated and stored for later WebAuthn work, visibly labeled as such.

Current code has `Tenant.Domains`, base-domain-first resolution, a process-wide `trust_proxy_headers` boolean and static `tls_cert_file`/`tls_key_file`. `Resolved.Issuer()` already uses the resolved host. Without `base_domain`, the first configured domain supplies the Management API audience. Codes, refresh tokens and several other grants do not yet persist their originating host. Plan 22's Deploy CLI template export is blocked by missing custom-domain discovery. These are migration inputs, not reasons to introduce a second independent domain list.

## 3. Public API and console contract

| Operation | Success | Scope |
|---|---|---|
| GET `/api/v2/custom-domains` | 200 array, `[]` if none | `read:custom_domains` |
| POST same | 201 pending resource | `create:custom_domains` |
| GET `/api/v2/custom-domains/{id}` | 200 resource | `read:custom_domains` |
| PATCH same | 200 updated resource | `update:custom_domains` |
| DELETE same | 204 | `delete:custom_domains` |
| POST `/{id}/verify` | 200 current verification result | `update:custom_domains` |
| POST `/{id}/test` | 200 `{success,message}` | `update:custom_domains` (local conservative rule until sourced inventory confirms) |
| GET `/api/v2/custom-domains/default` | 200 resource, or `{domain: canonicalHost}` | `read:custom_domains` |
| PATCH same with `{domain: hostname}` | 200 selected result | `update:custom_domains` |

Match `/default` before `/{id}`. All operations enforce tenant isolation and current persisted operator grants as well as signed grants. Reserved system-tenant mutations fail. Bad bodies/unsupported fields are 400; absent or foreign IDs 404; hostname/default/CAS conflicts 409; body over 64 KiB 413; throttled network operations 429 with Retry-After; unavailable repository/provider infrastructure 503 without partial success. Standard authentication errors remain 401/403. Do not copy upstream error prose.

Create requires `domain` and `type` (`auth0_managed_certs` or `self_managed_certs`). IDs use `cd_` plus 16 random bytes encoded hex. `domain` and `type` are immutable; change by delete/recreate with fresh proof. Optional `verification_method` accepts only `txt`; omission means TXT. `tls_policy` accepts only `recommended`, enforced locally as TLS 1.2 minimum with modern Go defaults and no legacy CBC/static-RSA suite opt-in. No `compatible` success. For self-managed public TLS this describes the required proxy policy; zeroauthy enforces it on its origin listener and checks the edge certificate through diagnostics, not by pretending to control the proxy.

PATCH accepts `tls_policy`, `custom_client_ip_header`, `domain_metadata`, `relying_party_identifier`. Header enum: `true-client-ip`, `cf-connecting-ip`, `x-forwarded-for`, `x-azure-clientip`, empty or null; omitted create value is `x-forwarded-for`, empty/null disables the override. Metadata is at most 10 string properties, values at most 255 Unicode characters; `{}` clears, null is rejected. RP ID must be the domain or a DNS-label ancestor that is not a public suffix; null on PATCH clears; no runtime WebAuthn claim. Read-only fields are rejected on writes, including `status`, certificate/verification state and `primary`. `primary` is a deprecated response compatibility field, always false locally; `is_default` reflects the default pointer, not creation order.

List sorts by `domain:1`; reject other sorts. `fields`/`include_fields` project only documented public response fields, never internal secrets. Local `q` subset: exact quoted `domain`, `status`, `type` terms joined by `AND`, at most 1,024 bytes/eight terms; unsupported Lucene syntax returns 400 rather than an unfiltered result. Freeze this documented compatibility difference. At most 100 API-managed domains per tenant, including failed/pending rows. Grandfather larger migrated lists; only additions are blocked until below the cap.

Default changes are atomic and require a currently usable custom domain. Selecting canonical clears the pointer. Deleting the selected custom domain falls back to canonical atomically. No automatic selection of the first ready domain. No implicit relocation of existing sessions, applications or API audiences. If the selected domain later becomes suspended or its certificate expires, keep the configured pointer for recovery but show it as unavailable. New implicit default-based notifications fall back to canonical; explicit header selections of an unusable domain fail 503. GET default reports the configured resource and its current status, not a fabricated ready fallback.

Console: replace the Plan 16 placeholder with a list and domain detail. Show DNS proof, routing target, verification versus certificate progress, expiry/renewal errors, default selection, proxy instructions and an explicit one-time secret reveal after verification. Label compatibility-only RP ID. Never store the proxy secret in local/session storage, URL, analytics or persisted draft. A lost verify response may lose the one-time key; explain recreate/reconfigure recovery and do not automatically retry verification. Failed reads lock writes; stale tenant responses cannot overwrite the current view; network progress is polled with cancel-on-navigation. Inputs and copy buttons have labels, keyboard focus and narrow-screen layouts. Hosted wildcard settings are deployment configuration, not tenant-editable credentials.

## 4. Registry, migration and canonical identity

One globally unique hostname registry owns canonical hosts, legacy/operator aliases, API custom domains and private origin aliases. Normalize DNS names with IDNA lookup mapping, lowercase and one optional terminal dot; reject schemes, paths, userinfo, ports, IP literals, wildcards, single-label/public-suffix-only names, empty labels, labels over 63 bytes and normalized DNS names over 253 bytes for the public API. Legacy/operator aliases retain existing `localhost:port` support. Customer API domains cannot be the system host, `base_domain`, any descendant of it, or the configured origin namespace. Existing reserved/overlapping records must produce an actionable migration error rather than silently change tenants.

Add a persisted immutable `Tenant.CanonicalHost`: initialize from the existing base-domain host, otherwise the first existing domain, before serving requests. Use it for the canonical Management API audience and canonical notification fallback. Verify existing managed Management API identifiers match; fail startup on unexplained drift rather than rewrite grants. A later base-domain configuration change requires an explicit migration, not implicit audience rotation. New no-base tenants still require an operator-configured canonical host. Tenant domains now project active registry aliases; pending API custom domains never enter resolver-visible domains. Legacy order is retained and canonical identity is independent of subsequent sorting/default changes.

Existing seed/system `domains` are privileged operator assertions. Migrate once as `operator` aliases, active with existing static/proxy TLS, without fabricating ACME certificates or changing them into API-owned records. These aliases remain visible in the system API but are excluded from Auth0 custom-domain list/default selection. Existing URLs and fixtures keep working. System/seed domain replacement reconciles only operator-owned aliases and preserves API-owned rows. It cannot remove the pinned canonical host. Omitted seed domains preserve state; explicit domains retain the existing apply/create-only semantics. Public domain CRUD can never bypass DNS proof by invoking privileged reconciliation. All writers and tenant creation/deletion participate in the same transactional global hostname uniqueness rules. Tenant deletion removes its aliases, domains, challenges, certificate references and default pointer; deployment ACME account/wildcard records survive.

Migration 0020 stores new domain/control tables and canonical/origin fields in memory, SQLite, PostgreSQL, MySQL and additive gRPC. Schema migration preserves raw existing fields; startup's configuration-aware reconciliation initializes canonical hosts/registry once transactionally before listeners/workers. A crash retries safely and never restores deleted API domains or overwrites API edits. Old plugins produce a clear capability error at startup, not a fallback to unverified domain routing. This migration requires a coordinated rollout: drain and stop pre-Plan-23 application nodes before schema/reconciliation changes, then start the upgraded fleet. Do not mix old and new nodes on the same live store/load balancer; the old resolver and grant validators do not enforce the new registry/proxy/origin rules.

## 5. Proof, readiness and removal

Create stores a fresh 32-byte random proof, publicly represented as a TXT value `zeroauthy-domain-verification=<base64url>` at `_zeroauthy-domain-verification.<domain>`. The record name/value are local opaque values, not copied vendor infrastructure. Tokens change on recreate and are bound to tenant, ID and generation. Public DNS proof and ACME validation are separate checks.

Use a deployment-configured DNS resolver, never a tenant-supplied nameserver or URL. Queries have a five-second total deadline, at most eight CNAME hops and 64 KiB accumulated records. TXT matching joins chunks of one RR but never combines different RRs; compare the full expected value. NXDOMAIN, missing/wrong proof and timeouts never grant ownership. Verification endpoints allow one attempt per domain per 30 seconds and 20 per tenant per minute, enforced across instances. Automatic retry delays are 1m, 5m, 15m, 1h, then 6h with ±10% jitter. After 72h pending, pause retries and show failure; manual verify restarts that schedule using the same proof. Self-managed activation occurs only in an explicit verify call so a background worker cannot consume the one-time proxy key.

Public lifecycle: `pending_verification` until proof and serving prerequisites are satisfied; `ready` only while usable; `failed` for exhausted initial provisioning, invalid configuration or expired unusable certificate. Internally distinguish proof pending/verified, issuing, active, renewal-error, suspended and deleting. Project only sourced public certificate/verification enums; keep detailed local reasons in operator diagnostics. A ready managed domain remains ready through a renewal error while its last certificate remains valid. Failed initial issuance can resume without a new domain ID. DNS ownership is rechecked before each issuance/renewal, and every 24h for self-managed domains. Loss after a prior success suspends routing only after 24h of continuous failed checks; resolver outages count as uncertainty, not immediate ownership revocation. After the grace period, re-prove before reactivation; an already established self-managed key is not reissued.

`server.custom_domains.origin_domain` names an operator-controlled DNS suffix (defaults to `base_domain` when nonempty). Create a random single-label `cd-<hex>.<origin_domain>` alias per API domain; reserve it globally against tenant canonical names. Operator wildcard A/AAAA DNS directs these aliases to the service. A managed customer may CNAME to it or route A/AAAA directly; the TXT proof is still required. A self-managed proxy connects using this origin host as both Host and SNI and sends its proxy key; the origin alias is never an issuer, redirect destination or browser login origin. Self-managed creation requires an operator static certificate covering the origin namespace or the hosted wildcard configuration below. Do not issue per-origin certificates on incoming requests.

Delete atomically removes serving eligibility, invalidates proof/key/worker generation, clears the default and schedules secret/challenge cleanup. Every request and TLS handshake consults current registry eligibility; an old parsed certificate cache cannot resurrect a deleted name. No new request is served on an already-open connection after deletion. Unknown host/SNI fails closed; store outages return 503 (HTTP) or abort the TLS handshake. Domain recreation needs new proof and cannot reuse a deleted tenant's certificate/key. Certificate revocation on deletion is best-effort asynchronous; local denial never waits for the CA.

## 6. Proxy and origin boundaries

Add `server.trusted_proxy_cidrs`. New self-managed origin traffic requires TLS, immediate-peer CIDR trust and constant-time validation of the domain's `cname-api-key` hash. Generate 32 random bytes and return the plaintext only in the first successful explicit verify response, after committing its hash and ready state. Duplicate concurrent verification has one key winner. No GET/list/test/export returns it; repeated verify does not regenerate it. Delete/recreate is the documented recovery path.

Map the private origin alias to the public custom domain from the stored record. Do not use `X-Forwarded-Host` to choose a different public origin for that route. Public self-managed host requests also require the same authenticated proxy boundary; knowing the public Host alone is insufficient. Strip the proxy key and ignored forwarding headers before downstream handlers/scripts/logging. A key from tenant A cannot authenticate tenant B's origin.

Only after proxy authentication, use its configured client-IP header, containing exactly one syntactically valid IPv4/IPv6 address (no comma lists, ports or zone suffix). Missing/invalid selected header returns 400 before attack-protection state changes; disabled override uses the peer. Existing non-custom routes keep the documented legacy trust behavior when only the old boolean is configured; emit a startup deprecation notice. When trusted CIDRs are supplied, restrict legacy forwarded-host/IP use to those peers too. Direct managed TLS enforces normalized Host equals SNI (421 on mismatch) and ignores forwarded-host spoofing. System-host operator tokens remain bound to the system origin.

## 7. ACME, certificate storage and hosted wildcard

Use the already pinned `golang.org/x/crypto/acme` client, not one independent `autocert.Manager` per instance: a cache alone does not serialize orders or distribute active challenges. `internal/keycert` remains token-signing certificate representation, not TLS management. Create `internal/certificates` for TLS policy, ACME coordination, secrets and challenge serving; `internal/customdomain` owns proof, lifecycle and routing.

Configuration is explicit opt-in:

| Setting | Default / rule |
|---|---|
| `server.acme.enabled` | false; API managed creation fails 503 when disabled |
| `server.acme.directory_url` | Let's Encrypt production directory; HTTPS only, deployment controlled |
| `server.acme.email`, `terms_accepted` | valid contact and explicit true required when enabled |
| `server.acme.deployment_id` | required stable nonempty identifier shared by replicas |
| `server.acme.challenge` | `http-01` or `tls-alpn-01`, explicit choice; no hidden fallback |
| `server.acme.http_listen` | `:80` for HTTP-01; empty for TLS-ALPN-only |
| `server.acme.ca_bundle_file` | optional additional CA trust roots; never disable validation |
| `server.acme.workers` | 2 per process, range 1–8; persistent leases coordinate replicas |
| `server.acme.hosted_wildcard.enabled` | false; requires portless DNS `base_domain` and DigitalOcean zone/token |
| `server.acme.hosted_wildcard.zone`, `token_file` | explicit containing DNS zone; credential file, not tenant state or seed export |
| `server.custom_domains.origin_domain` | `base_domain` or explicit operator suffix; hosted wildcard covers only its matching suffix |

Keep current static TLS and externally terminated HTTP modes when ACME is off. With ACME on, static certs may cover canonical/system/operator-origin hosts; exact managed domain certificates take precedence. Validate static SAN coverage at startup, never silently serve a default cert to an unrelated SNI. Hosted wildcard and static overlap prefer exact static canonical/system identity, then exact managed certificate, then eligible hosted wildcard. A no-base or out-of-suffix system host needs its static certificate; do not ACME-issue it implicitly. Production HTTP-01 requires public port 80 reaching the challenge listener; TLS-ALPN requires public 443 reaching the TLS listener without ALPN termination. Local tests map standard external ports to isolated container ports.

Persist encrypted ACME account keys, pending order keys, certificates/private keys and TLS-ALPN challenge private keys using `keys.Wrapper`, with versioned AAD containing deployment ID, record kind/key, tenant/domain generation where applicable. Account identity includes deployment ID and directory URL; staging/production never share it. DNS credentials remain in deployment files/environment. A replica with the wrong wrapper key fails without ordering replacements. Public API and logs never include private PEM, proxy keys, account credentials or raw upstream response bodies.

A lease has resource key, owner, monotonically increasing fencing token and expiry. Duration 120s, heartbeat 30s; use storage time for expiry decisions, and reject commits at `now >= expiry`. Claim/renew/check/commit are atomic across SQL handles and gRPC instances. Never hold a database transaction over DNS/ACME calls. Save order URL/key/intent before subsequent network steps; a surviving worker resumes it. Recheck lease and domain generation in the same transaction publishing the certificate and ready state. Loss of lease cancels work; stale workers cannot publish, remove a successor's challenge or update its retry schedule. Exact-once external CA orders are not promised after a response-loss crash; bounded retries, persisted order URLs and fencing prevent routine duplicate issuance and stale publication.

Share active HTTP-01 token/key authorization and TLS-ALPN challenge material through the store so any replica can answer. HTTP listener serves only exact active `/.well-known/acme-challenge/<token>` GET/HEAD requests; unknown tokens/hosts are 404, no redirect and no tenant auth. Other HTTP traffic redirects GET/HEAD only to an already active registered HTTPS origin, preserving a safe relative path/query; unsafe methods fail, and arbitrary Host headers never become Location. TLS challenge certificates are served only for matching live challenge SNI plus `acme-tls/1`. Ordinary handshakes never see them. TLS callbacks perform bounded store/cache reads, never DNS or ACME issuance.

Validate issued chain, SAN set, EKU/server use, key match, validity, and expected trust before atomic publication. Default renewal begins at two-thirds of actual certificate lifetime with deterministic per-resource jitter up to 5% of lifetime, always before expiry; short-lived test certificates use the same rule. Honor CA Retry-After with capped one-minute-to-six-hour exponential backoff; never serve expired certificates or log an issuance failure as success. Cache parsed certificates by stored revision, with registry eligibility checked each handshake. Durable order/challenge records expire/clean up after completion or failed recovery, bounded to 24h; worker shutdown cancels work and releases leases where possible.

Hosted extension: obtain SANs `base_domain` and `*.base_domain` via DNS-01 using the same account/lease/cache system. It covers one tenant label and the default system host, not arbitrary-depth names. Keep apex routing behavior unchanged. DNSProvider has `Present` returning an owned record ID and `CleanUp` deleting only that ID/value; no broad TXT replacement. Support simultaneous apex/wildcard TXT values at the same owner. Persist intent before create, record returned IDs, recover via exact name/value inspection without adopting/deleting pre-existing records. Do not follow DNS challenge CNAME/NS delegation in this first provider; report unsupported delegation. Resolver propagation deadline 10m, polling 5s–30s. DigitalOcean API requests are bounded to 10s and use the fixed provider host; tenant content cannot alter provider URL or authorization. Tests use a fake provider API and authoritative local DNS. Real-provider smoke testing is optional and separately authorized; local CA issuance is mandatory acceptance.

## 8. Authentication, links and diagnostics

The public request origin determines discovery URLs, `iss`, `/userinfo` audience and hosted-page `custom_domain` context (`domain` and bounded metadata only). API identifiers, especially the canonical Management API audience, stay constant. Local Management API tokens must have the serving public origin as issuer; do not accept a token from every alias merely because tenant ID matches. Console operator-token checks retain their separate system-issuer path.

Persist `Origin` on new auth transactions, authorization codes, PAR requests, device grants, sessions, refresh tokens and reset/verification tickets; propagate it through issuance/rotation. Reject cross-origin redemption before consuming a code, rotating/revoking a refresh family, counting an authentication failure or mutating a ticket. Bind authorize-to-code-exchange, device activation/polling and logout to the public origin. Cookies remain host-only with existing Secure/HttpOnly/SameSite semantics. Changing default has no effect on in-flight origins. Deleting an origin denies new use but does not rewrite JWTs already issued; custom API verifiers retain their configured issuer policy.

Legacy rows with no Origin are interpreted as pinned canonical origin, not whichever host presents them first. Existing canonical flows keep working; pre-upgrade noncanonical sessions/refresh grants and in-flight links may require reauthentication/reissue. This deliberate upgrade boundary must be highlighted in release notes and covered by fixtures. Preserve grant expiry, CAS and replay semantics in every driver/codec.

For user-facing URLs created by supported Management API ticket and verification-email-job operations, resolve `auth0-custom-domain` (explicit ready same-tenant domain or canonical) → default → canonical. Do not use arbitrary request Host as a notification choice. Reject invalid selections before creating jobs/tickets; persist the chosen origin on async jobs so later default changes do not retarget them. Authentication-triggered reset/signup/verification/welcome/security workflows keep the originating public domain. Existing queued jobs without selection use canonical. Recheck the selected origin's same-tenant ownership and usability immediately before an async job creates tickets or sends mail. If unavailable, fail the job with a safe visible error, send nothing and do not silently retarget; a new request can choose a usable domain. A default change alone never fails or retargets an otherwise usable bound job. Internal export/download URLs and system operator setup links retain their existing host rules. Email/hosted templates receive public domain context, never origin aliases or keys. Branding preview uses an explicitly synthetic example domain/metadata without resolving a real tenant hostname.

`POST /{id}/test` diagnoses a known verified domain without changing ownership/default/key state. It resolves public IPs and fetches only `https://<domain>/.well-known/openid-configuration`, checking TLS trust/hostname, expected public issuer and required endpoint origins. Ten-second overall budget, 64 KiB response, no redirects, at most two resolved addresses. Reject every private/loopback/link-local/multicast/unspecified/reserved address, IPv4-mapped equivalent and mixed public/private answer; pin an approved address in the dialer while preserving hostname SNI, disable environment proxies and validate again on retry. A domain changing DNS to an internal address cannot turn diagnostics into SSRF. Only a constructor-injected test dialer allows isolated fixtures; no production insecure switch. Success means this bounded probe passed, not every proxy/SDK configuration. Not-ready domain returns 409, observed failure returns 200 with `success:false` and original safe explanatory text, infrastructure failure 503. Same distributed attempt limits as verify.

## 9. Acceptance and implementation rules

Keep Go 1.26.7 and the existing Vue/TypeScript toolchain. Reuse existing cryptography and ACME packages; any new DNS parser dependency needs a pinned version/license record. No public CA issuance, real DNS writes or credentialed upstream observations in CI. This planning task runs no product tests and makes no DNS/CA mutations. The Plan 19 database hold is specific to Plan 19; Plan 23 database tests should run with their owning tasks.

| Acceptance | Required evidence |
|---|---|
| AC1 | Nine-operation sourced inventory, pinned SDK/CLI, scopes, limits, errors, default/list semantics |
| AC2 | Global host claims, canonical audience stability, memory/three SQL/gRPC CAS/rollback/cascade and schema-0019 upgrade fixtures |
| AC3 | TXT proof, retry budget, proof loss/recovery, one-time key races and stale-generation rejection |
| AC4 | Real Pebble HTTP-01 and TLS-ALPN-01 issuance, restart, forced renewal, expiry and multi-instance challenge serving |
| AC5 | Real local DNS-01 apex/wildcard issuance via fake DigitalOcean API; provider ownership/cleanup, two replicas and crash recovery |
| AC6 | Trusted proxy/key/IP handling, direct Host/SNI mismatch, SSRF diagnostics and safe challenge redirects |
| AC7 | Origin-bound grants, stable audiences, independent cookies, default-selected async links, baseline auth/email/protection behavior |
| AC8 | Accessible console, one-time secret loss behavior, stale tenant replies, error and uncertain-write handling |
| AC9 | Four strict Deploy CLI migration modes; real custom-domain records; Plan 22 nonempty template round trips; default import readiness boundary |
| AC10 | Full Go race/SQL, generation twice, console, source checks, domain/branding/email/default E2E and local conformance; exact warnings/skips recorded |
| AC11 | Operator guide for ports, DNS, proxy trust, secrets/backups, renewal, migration, rollback, local differences and stored-only RP ID |

Deploy import does not prove ownership or transport proxy secrets/certificates. Import domain declarations as pending, verify in a separate explicit step, then import defaults. A one-shot import demanding an unverified default must fail clearly. YAML/directory × generated/preserved credentials must test this boundary, then a staged successful round trip. Domain IDs/proof/certificate state are target-local; strict comparison preserves domain/type/header/metadata/TLS/RP ID/default and detects missing families or changed values. Removing the former custom-domain-discovery block must also exercise the pinned branding handler's `body` expectation against the sourced template contract; do not claim the old `template` fixture alone proves compatibility. Pinned Deploy CLI 9.1.0 only accepts `true-client-ip`, `cf-connecting-ip`, `x-forwarded-for` or null: `x-azure-clientip` and empty string remain supported API values but are explicit tool-unavailable round-trip cases, tested for rejection without normalization or silently narrowing the API. The CLI only applies `is_default:true`; importing a canonical-default source cannot clear a pre-existing target custom default. Require an explicit Management API canonical-default preparation step for that case, and test failure of strict comparison without it. ACUL stays excluded.

Alternative considered: proxy-only support postpones the explicit roadmap's automatic/wildcard hosting goal. Per-process autocert is simpler but cannot supply fenced shared challenges/order recovery. The selected explicit registry plus bounded worker costs more storage work, but makes the state transitions testable. Task implementation details may vary only where they preserve these contracts; new product choices must be recorded, not silently inferred as maintainer approval.

## 10. Design check and author decisions

A fresh read-only builder check on 2026-10-26 identified two consequential gaps: pinned-tool header/default limits and notification behavior after a domain loses readiness. Sections 3, 8 and 9 now settle both. These are author choices for maintainer review. Other explicit choices are preservation of operator aliases, immutable canonical audience, TXT API proof, background fenced ACME, strict proxy admission, the legacy canonical-origin interpretation, and DigitalOcean-only hosted DNS-01. No implementation or runtime verification was performed while drafting.

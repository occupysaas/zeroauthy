## 1. Outcome and scope

An operator can make the tenant's hosted authentication pages match its brand, edit page structure and localized copy, and choose an identifier-first database login. Management API writes must change the rendered experience. The console exposes the same configuration with an isolated preview. Existing installations without new configuration keep their current appearance, text, authentication behavior and seed semantics.

Included: branding settings, theme lifecycle, Universal Login page templates, prompt settings, custom text, safe partials, identifier-first database login, memory/SQL/gRPC persistence, console editors, SDK/CLI/deploy migration and local browser coverage. Keep Go 1.26.7 and the existing Vue/TypeScript toolchain. Reuse the Plan 21 bounded Liquid evaluator through a neutral package; do not introduce a second general-purpose interpreter or change email semantics.

Excluded: custom domains/certificates (Plan 23), social discovery (24), Actions validation/execution (27–28), organizations (29), WebAuthn/MFA/passwordless (33–34), Classic Login's hosted JavaScript runtime, and Advanced Customizations for Universal Login (ACUL). ACUL requires its own client SDK/protocol design; do not expose successful inert screen-rendering APIs. No asset hosting, remote template fetching, filesystem template override directory, or copied Auth0 widget DOM. The old template-directory follow-up is superseded by tenant templates, not silently implemented as a second precedence layer.

**Local design recommendations:** security restrictions, fallback policy, limits, theme activation and future-feature disposition below are local choices, not observed Auth0 behavior; execution rulings and their costs are preserved in the implementation record. This design deliberately narrows the roadmap's promise that every Auth0 template runs unchanged. Supported Liquid/HTML templates round-trip; scripts and unsupported capabilities fail validation with a documented difference. The maintainer authorized Plan 22 implementation on 2026-10-25.

## 3. Management contract

All paths below have `/api/v2` prefix. Reuse the existing Management API error envelope, tenant host resolution, persisted operator grants, M2M scopes and reserved-system-tenant write restrictions. Read/write scope families are `branding` and `prompts`; Task 1 freezes each operation's exact verb scope, including theme create/delete and template operations. Do not invent a theme list endpoint.

| Operations | Resource and behavior |
|---|---|
| GET/PATCH `/branding` | `colors.primary`, `colors.page_background`, `favicon_url`, `logo_url`, `font.url`; validated merge with omission preserved |
| GET/PUT/DELETE `/branding/templates/universal-login` | One page template; preserve the documented HTML versus JSON wire representation per operation |
| POST `/branding/themes` | Create a complete theme, generate its ID, make it default atomically under the local lifecycle below |
| GET/PATCH/DELETE `/branding/themes/{themeId}` | Tenant-scoped theme read/update/delete |
| GET `/branding/themes/default` | Active default; register before the parameter route |
| GET/PATCH `/prompts` | Experience and identifier-first settings; future WebAuthn setting visibly stored-only |
| GET/PUT `/prompts/{prompt}/custom-text/{language}` | Replace one language/prompt override map, preserving all other overrides |
| GET/PUT `/prompts/{prompt}/partials` | Replace one prompt's screen/slot map; empty map clears it |

**Local lifecycle:** absent branding returns legacy effective fields, absent prompts returns `new`, identifier-first false and WebAuthn false; absent template/default/named theme returns 404; absent custom text/partials returns `{}`. Template DELETE is idempotent 204. Theme create returns 200; newest created theme becomes default, older records remain addressable. PATCH does not activate another theme; deleting the default clears the pointer and restores base branding, without reactivating older themes. Missing theme PATCH/DELETE returns 404. Theme IDs are 32 alphanumeric characters. Task 1 must confirm or explicitly retain these choices as differences. GET/PUT/PATCH generally return 200; template PUT's empty response/media type must follow the frozen contract, not a guessed JSON wrapper.

Nested PATCH changes only supplied members, including false/zero values. Null clears optional URL fields; null required colors/objects fails. PUT replaces the addressed document and validates its required fields; unknown properties fail unless explicitly inventoried as future fields. Size checks occur before JSON/HTML decoding. Concurrent changes use revision compare-and-swap with at most three fresh-read attempts, then a conflict; never overwrite unrelated configuration from a stale tenant snapshot.

`universal_login_experience:new` is active. `classic` and `webauthn_platform_first_factor:true` are stored and returned for migration but labeled not enforced; the existing zeroauthy login remains effective. No passkey button or Classic runtime is implied. Custom text and partials for inventoried future prompts can be stored, but the console marks them unavailable until their flow ships. Arbitrary unknown prompt/screen names fail. ACUL routes remain unsupported and its deploy handler stays excluded.

## 4. Persistence and precedence

Add a tenant-scoped `HostedLoginConfig` repository with one versioned aggregate: branding overrides, templates, theme records/default ID, prompt settings, partials, and custom text. This is deliberately one bounded configuration snapshot so each request sees a coherent revision. It contains no credentials. Keep transaction state separate. Grandfather existing aggregates above 1 MiB without truncation: migration and reads preserve them; subsequent writes must strictly reduce serialized aggregate size until it is within 1 MiB, then the normal cap applies. The 2 MiB per-request cap remains; resource-level clearing/replacement permits incremental remediation. Render budgets still apply, with the safe fallback below. Surface an operator warning and test this migration explicitly.

Migrate existing `Tenant.Branding` and `Tenant.CustomText` into the aggregate exactly once; explicit empty/false values remain distinct from absence. Change seed application, Management writes and runtime resolution to use the aggregate as authority after migration. Retain legacy fields only for backward decoding and the no-record fallback, never as a second writable source. Seed's existing ownership rules continue: omitted new seed sections preserve API settings; explicit sections update only their owned values through the same rules. Existing theme IDs/default pointers survive unrelated seed reruns. All localization consumers, including email service, verification, reset and security notifications, must load canonical custom text into a request-local tenant view before constructing `i18n.Localizer`; never mutate a shared tenant object or continue reading stale legacy overrides. Email and hosted pages therefore see the same saved text revision on their next operation.

Memory, SQLite, PostgreSQL, MySQL and gRPC implement deep copies, CAS, rollback and tenant cascade deletion. Migration `0019_hosted_login.sql` follows `0018_email.sql` in each dialect (renumber if execution has advanced). Additive proto fields and explicit unsupported-repository errors prevent an old plugin from silently discarding configuration. An upgraded plugin is required for writes; a repository-unavailable error is not interpreted as an absent record.

Runtime precedence, per field: built-in original defaults → migrated legacy/base branding → active theme. Page templates wrap the widget; they do not change that precedence. Catalog text uses existing locale negotiation, then the selected prompt/language custom override, then the existing catalog fallback. Never copy an entire theme's defaults over explicitly configured base branding merely because a theme property is absent. On delete, the next request sees the fallback across all server instances; no process-global tenant cache. A render uses one snapshot; concurrent changes affect subsequent requests.

## 5. Rendering and safety

Introduce `internal/liquid` for the bounded evaluator and `internal/hostedlogin` for context projection, template/partial validation and composition. `internal/ui` retains ownership of original Go widget templates and CSP. Preserve email parsing, escaping, limits and errors with regression tests during extraction.

**Local limits:** template source 100 KiB UTF-8; each partial 10,000 Unicode characters and at most 40 KiB; aggregate configuration 1 MiB; Management/preview request 2 MiB; variable context 64 KiB; output 512 KiB; nesting 32; loop iterations 10,000; evaluation steps 100,000; deadline 100 ms; eight active renders per process. Check budgets during parsing, loops and output construction, not just afterward. Reject overload without spawning unbounded goroutines. Theme collection maximum 20 per tenant is a local bound, not a claimed Auth0 quota.

Validate Liquid syntax at write time. Support the existing evaluator's documented subset plus `auth0:head` and `auth0:widget`, including whitespace control. Require exactly one head tag and at least one widget tag in source; at render time require exactly one emitted head and exactly one emitted widget to avoid duplicate IDs/forms (multiple mutually exclusive widget branches may be accepted). Missing/duplicate output fails safely. Tags insert only trusted renderer-owned fragments. No includes, filesystem, network, reflection or recursive evaluation. Unsupported tags/filters fail save, never disappear silently.

Project explicit public fields under `application`, `organization`, `prompt`, `locale`, `user`, `branding`, `tenant`, `custom_domain`, `transaction`. Application/tenant fields are safe display metadata; prompt identifies current screen and localized text; user is absent before successful authentication and otherwise contains only display name if needed. Organization/custom domain remain empty until their plans. Transaction projection contains presentation hints only, never its raw object. Exclude passwords, tickets, CSRF secrets, cookies, tokens, code verifiers, private metadata and unvalidated request parameters. Unknown variables evaluate empty; variables never become executable source. Escape substitutions by HTML context; reject interpolation in tag names, event handlers, script/style content or unquoted attributes. URL attributes must pass scheme validation after interpolation. Only explicit head/widget/validated-partial values can be trusted HTML; user data cannot use a raw bypass.

**HTML/CSS policy (local):** accept semantic static HTML, links, images, stylesheet-free decorative markup and inline `<style>` blocks; allow no tenant script, event handler, iframe/object/embed/base/meta-refresh, nested form, `formaction` or executable URL. Parse HTML structurally, not with regular-expression sanitizers. Reject unsafe content at save and validate the rendered document again before inserting trusted widget fragments. Rewrite only approved style elements with a response nonce. Disallow style attributes, CSS imports, arbitrary CSS URLs and selectors targeting internal controls. Local CSS grammar: selectors are only `.za-decoration`; those elements may not contain a head/widget tag or trusted widget output. Allowed declarations are color/background-color (hex or numeric rgb/rgba), font-size 12–48px, font-weight 400/600/700, text-align left/center/right, and margin/padding 0–64px. No selector lists/combinators/pseudo selectors, variables, functions other than numeric rgb/rgba, at-rules, positioning, dimensions, display, opacity, transforms, clipping or negative spacing. Declaration/selector parsing must reject escapes or comments that obscure tokens. The widget has its own explicit typography/colors and normal-flow container. This limits decoration rather than promising universal visual accessibility: an operator can still choose poor theme contrast, which the console warns about. Templates cannot move or conceal mandatory controls through executable markup or arbitrary CSS. Theme CSS uses typed values serialized into fixed custom properties, never raw CSS fragments. This narrower styling contract is a documented difference.

Allow external images and WOFF/WOFF2 fonts only over HTTPS, with no userinfo; assets are browser-loaded, never fetched by the server. Keep external stylesheet/script sources disabled. CSP permits only the needed validated image/font origins plus existing built-in CAPTCHA resources; scripts remain renderer-owned and nonce-based. Preserve existing redirect-aware `form-action`, frame restrictions, base-uri, no-store and referrer policy. No wildcard additions, `unsafe-inline`, `unsafe-eval` or template-provided CSP. Preview disables all external loads even when production permits them.

Apply the wrapper/theme to login, signup, consent, tenant-resolved errors, logout confirmation/result, reset request/sent/form/success/error, verification, and device code/confirmation/result. Form-post and web-message protocol responses never use tenant templates. Errors before trustworthy tenant resolution and system-console authentication use built-in pages. Render to a buffer before headers/body; a malformed stored template or render budget failure returns the same functional widget in the built-in wrapper with a redacted warning. Store read failure returns a built-in 503 error page rather than pretending configuration is absent. Branding failure cannot change an auth decision, issue a token or suppress a required CAPTCHA/consent screen.

## 6. Identifier-first database login

When effective identifier-first is true, `/u/login` displays an identifier screen. Its POST validates existing cookie/state/CSRF bindings, normalizes using existing identity rules, and stores the identifier plus selected enabled database connection in transaction state. It then redirects to `/u/login/password`. This step never queries whether the account exists, calls a custom database login script, sends mail or records a wrong-password attempt. Login hints prefill; they do not skip verification or create a session.

The password GET/POST uses the stored identifier and connection; submitted replacements are ignored/rejected. It invokes the existing password authentication, block/breach/CAPTCHA checks and code/session completion exactly once. Existing combined login remains the default. Add a CSRF-protected `/u/login/identifier` POST to clear the selected identifier and return to step one. Keep original transaction expiry; transitions never extend it or modify validated authorize Params. Passwords are never persisted.

Persist a versioned hosted state on `AuthTransaction`: `Step` (`identifier`, `password`, `authenticating`, or empty legacy combined), `Identifier`, `ConnectionID`, `PromptFields`, `Revision`, `FormConfigRevision`, `FormScreen`. State changes are atomic against expected revision. Consume the password stage into `authenticating` before the external authentication call, so concurrent password submissions cannot authenticate twice. On an ordinary denied attempt, transition back to password with a new revision; a crash leaves the transaction unusable and the user restarts authorization. Successful completion deletes the transaction as today. A stale tab receives a localized restart message and cannot replay a transition. In-flight two-step transactions finish their captured flow even if an operator disables identifier-first; new transactions use the current setting. Tenant, client, cookie, CSRF, connection eligibility and expiry are rechecked at every step.

## 7. Partials and text

Render supported login, login-id, login-password and signup partials into the four documented form-content/form-footer slots; secondary-action slots and future prompt records are stored-only until their controls exist. No new signup split flow is implied. Partials use the same restricted Liquid/HTML policy, with labeled inputs/selects/textareas allowed only inside form-content slots. They cannot define core field names/IDs or replace buttons, state, CSRF, password, connection or redirect fields. Built-in authentication always wins.

Bind every rendered login/signup form to the configuration revision and screen in hosted transaction state; return its resulting hosted-state revision in a hidden field. On POST, require matching hosted-state revision, screen and current configuration revision before deriving the allowed field names from the same rendered partials. A changed configuration or stale tab requires redisplay without authentication or field capture. This rule also covers combined login and signup. When progressing identifier to password, preserve captured identifier-screen values; a successful password submission replaces values belonging to its own screen (including removal for unchecked checkboxes). Reject a field name declared on both screens to avoid ambiguous ownership. Resetting identification clears all captured fields. Configuration changes therefore never silently accept inputs the rendered form did not contain.

Capture only `ulp-` names from form-content controls in active partials, into transaction `PromptFields`, with a local limit of 30 fields, 128-byte names, 1 KiB per value and 8 KiB total. Reject duplicate names, files, unknown names and over-limit submissions with a localized validation error; permit missing checkbox values. Never persist password-type partial controls: reject them at save. Keep existing 16 KiB total hosted-form limit. Fields are untrusted, escaped on error redisplay and deleted with transaction expiry/completion. No user metadata, tokens, mail or logs receive them automatically. They do not provide server-validated legal consent or a business validation workflow in this plan.

The roadmap's `event.prompt` promise is corrected: public partials guidance describes captured fields under Actions `event.request.body`. Plan 27 must freeze its own trigger contract and validate this transient data; Plan 22 implements no Actions bridge or custom-database-script context extension. Document these limitations beside the editor.

Custom text remains compatible with Plan 4 locale negotiation and existing `${...}` placeholders. Add explicit mappings for the new identifier/password screens and supported `var-` custom variables; support at most 30 custom variables per screen/language. Preserve recognized future text without claiming it renders. Plain text stays escaped; any documented Markdown link support uses an allowlisted link-only renderer with HTTPS/mailto validation, never arbitrary raw HTML. Empty override maps remove overrides and restore catalog fallback. Existing seed-language case normalization and duplicate detection stay intact.

## 8. Console and migration

Replace the planned Branding page with Settings, Theme, Page template, Prompts and Text/partials editors. Show effective versus stored-only settings, reset/delete effects and seed ownership. Theme editor covers all active component fields with keyboard-usable controls and a structured JSON view for future fields. Do not present social/identifier configuration as active when no underlying control exists. Block writes after failed reads; preserve edits after errors; discard stale fetch/preview responses on tenant, prompt or locale switch. Unknown write outcomes cause a refresh and uncertainty message, never an automatic retry.

Add operator-only POST `/api/system/tenants/{tenant}/branding/preview`, resolving the target before checking signed and persisted grants. Require `read:branding` and `read:prompts`; no M2M access. Accept `{screen, language, overrides?}` for a finite screen list and validated unsaved aggregate overrides, returning `{html, warnings}`. Synthetic fixtures only: no tickets, users, real transaction, callbacks or authentication side effects. Limit body/rendering using §5 and impose per-process overload protection; this is not a distributed quota claim.

Display returned HTML only in a sandboxed `srcdoc` iframe with no allow-scripts, allow-same-origin, forms, navigation or popup capability, and a restrictive in-document CSP. Console DOM never consumes template HTML. Preview explicitly labels blocked external images/fonts and shows placeholders. There is no automatic live login initiated from preview.

Extend actual pinned node-auth0 and auth0-cli exercises where commands exist. Deploy CLI YAML/directory tests cover branding, themes, templates, prompt settings, text and partials with nonempty values and strict comparisons. Template export may require custom-domain discovery: do not fake verified domains to appease the tool before Plan 23. Record a genuinely blocked handler as tool-unsupported, keep that handler excluded, and exercise its underlying API through SDK; require real round trips for every unblocked handler. Do not enable ACUL or unrelated resource handlers.

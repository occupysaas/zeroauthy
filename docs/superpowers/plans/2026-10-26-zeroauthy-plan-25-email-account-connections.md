# Plan 25 — Microsoft and Google Email-Account Connections Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver Microsoft personal and work/school sign-in, and prove existing Google/Gmail/Workspace sign-in, while deferring other social providers.

**Architecture:** Add `windowslive` and `waad` adapters to Plan 24's federation service and shared rules. Microsoft-specific discovery and signing-key issuer validation stay separate from generic OIDC. Reuse attempts, sealed credentials/tokens, identity ownership, browser completion and all existing store implementations; no new persistence schema is expected.

**Tech Stack:** Go 1.26.7, existing go-jose and bounded HTTP transport, memory/SQLite/PostgreSQL/MySQL/gRPC stores, OpenAPI generation, Vue/TypeScript/Vitest, Playwright, node-auth0 7.4.0, auth0-cli 1.37.0 and auth0-deploy-cli 9.1.0. Node 25+ remains required only for the retained custom OAuth script acceptance lane.

**Spec:** [Email-account connections design](../specs/2026-10-26-zeroauthy-email-account-connections-design.md). Read both documents and the [Plan 24 implementation record](../2026-10-26-plan-24-implementation-record.md). Status: draft for review; every checkbox is prospective, and no implementation test result is claimed here.

## Global Constraints

- Keep Go 1.26.7 and the existing Vue/JOSE/store stack; no new production OAuth framework. Follow `CLEAN_ROOM.md`, original UI/copy and sourced compatibility decisions.
- Implement `windowslive` (personal, social) and `waad` (work/school, enterprise); retain `google-oauth2`, `oauth2` and back-channel `oidc`. No other new social strategy.
- Microsoft public cloud only; v2 code/query flow, S256 PKCE, independent state/nonce, `client_secret_post`, scopes exactly `openid profile email`. No Graph/UserInfo calls, offline_access, mailbox APIs or arbitrary upstream/assurance forwarding.
- Personal authority `consumers`; single-directory validated GUID/DNS authority; explicit multitenant `useCommonEndpoint: true` uses `organizations` and rejects a supplied tenant_domain. It accepts every organizational tenant and rejects the consumer tenant.
- Consumer tenant is `9188040d-6c67-4c5b-b112-36a304b66dad`. Microsoft ver must be `2.0`; require verified issuer/tid/key-issuer binding. Generic OIDC keeps exact issuer validation.
- RS256 only; clock skew 60 seconds; validate present nbf. HTTPS/public pinned addresses, no redirects/proxy, 10 seconds/request, 30 seconds callback total, 1 MiB decoded response, 100 JWKS keys, 64 KiB token/profile values.
- Cache TTL at most five minutes and 256 entries/process, scoped by tenant/connection/revision/authority/JWKS; one coalesced unknown-kid refresh. Attempts expire at min(transaction expiry, five minutes).
- Secrets are write-only and sealed; token projection needs read:user_idp_tokens on individual-user reads. No automatic email linking; email may be missing; Microsoft email_verified must not become true.
- Identity formats are spec §6's exact local contracts. Existing Google/OAuth/OIDC identities remain byte-for-byte unchanged. No retroactive edit to migration 0021, no automatic legacy Microsoft-ID conversion.
- No real provider/tenant calls in CI. Optional live evidence is separate and unavailable means not run. Plan 19's database-test hold remains specific to Plan 19; this plan does not alter it.

## Review Focus

1. Equal oid/sub or email in two organizational tenants must create distinct identities; a consumer or mismatched signing-key issuer must never authenticate through waad (Tasks 3–5).
2. A work/school ID token without email, or with an email-shaped preferred_username, must succeed without inventing verified email or merging an existing account (Tasks 4–6).
3. A shared Microsoft discovery issuer template must not weaken generic OIDC or pin a multitenant connection to its first user (Tasks 3, 6).
4. Imported legacy Microsoft identities or a rolling old writer must not silently change lookup ownership or database email indexes (Tasks 5, 9).
5. A Deploy CLI round trip that loses provider credentials or external script content must fail rather than produce a configuration that looks complete but cannot log in (Task 8).

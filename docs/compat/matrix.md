# Compatibility Matrix

Status of Auth0-compatible surfaces in zeroauthy.

| Surface | Status | Notes |
|---------|--------|-------|
| Discovery (`/.well-known/openid-configuration`) | Implemented | Advertises only implemented grants; `/authorize` is now served; advertises `end_session_endpoint` (`/oidc/logout`) and `revocation_endpoint` (`/oauth/revoke`) |
| JWKS (`/.well-known/jwks.json`) | Implemented | current, next, previous keys |
| `/oauth/token`: `client_credentials` | Implemented | Verified with @auth0/auth0-auth-js 1.16.1, auth0/legacy 7.4.0, express-oauth2-jwt-bearer 1.11.0 |
| `/authorize`: `response_type=code`, PKCE (S256), `response_mode` query / fragment / form_post / web_message, `prompt` none / login, `max_age`, `connection`, `screen_hint=signup`, `login_hint` | Implemented | Verified with @auth0/auth0-spa-js 2.28.3 (login, silent auth, reload) |
| `/oauth/token`: `authorization_code` | Implemented | ID token with `at_hash`, `sid`, `nonce` |
| `/userinfo` (GET, POST) | Implemented | |
| Hosted login: `/u/login`, `/u/signup` | Implemented | Database connections only |
| `/oauth/token`: `refresh_token` (rotation, reuse detection, leeway) | Implemented | Rotation verified with @auth0/auth0-react 2.28.2 (m5-react); reuse rejection is checked by a raw HTTP replay of the tokens the SDK rotated, not by an SDK call; @auth0/nextjs-auth0 4.32.0 obtains a refresh token via `offline_access` (observed in the server log, not asserted) but does not exchange it, and its server-side `/oauth/revoke` at logout was seen in the server log but is not asserted; leeway covered by server tests only. Opaque, stored hashed; no fixed length is promised (Auth0 lengthened its tokens in 2026-10) |
| `/oauth/revoke` | Implemented | Refresh tokens (whole family); JWT access tokens are not revocable |
| `/v2/logout`, `/oidc/logout` (RP-Initiated Logout with confirmation) | Implemented | `/v2/logout` verified with @auth0/auth0-react 2.28.2 (m5-react); `/oidc/logout` verified with @auth0/nextjs-auth0 4.32.0 (m5-nextjs, with `id_token_hint`, so no confirmation); the confirmation page and `returnTo`/`post_logout_redirect_uri` rejection are covered by server tests only; `federated` ignored; no back-/front-channel logout |
| `/oauth/token`: `password`, `http://auth0.com/oauth/grant-type/password-realm` | Implemented | Password-realm verified with auth0/legacy 7.4.0 (`oauth.passwordGrant` with `realm`: access, refresh and ID tokens; the refresh token then works with `oauth.refreshTokenGrant`) and @auth0/auth0-auth-js 1.16.1 (`getTokenByPassword` with `realm`, which sends `grant_type=password`: access token, verified against a non-default custom database connection in m9); the plain `password` grant without a realm (tenant `default_directory`) and brute-force throttling are covered by server tests only (D-0017) |
| `/dbconnections/signup` | Implemented | Verified with auth0/legacy 7.4.0 (`database.signUp` returns `_id`) and @auth0/auth0-auth-js 1.16.1 (`database.signUp`); undocumented error bodies use `{error, error_description}` (D-0018), covered by server tests only |
| `/dbconnections/change_password` and hosted password reset (`/u/reset-password`) | Implemented | Verified with auth0/legacy 7.4.0 (`database.changePassword` succeeds and a reset email is written; an unknown address also succeeds) and @auth0/auth0-auth-js 1.16.1 (`database.changePassword` returns the plain-text confirmation, the same for an unknown address). An unknown user gets the same 200 and no email (D-0018: the auth0-auth-js README's behaviour, chosen over the API reference's 404); server tests assert identical bodies and that no email is sent. Hosted flow verified in Chromium (m7-reset): "Forgot password?" link, emailed single-use link, new password, sign-in with it. Ending all sessions and refresh tokens on reset is covered by server tests only (D-0019) |
| Custom database connections (`enabledDatabaseCustomization`, `import_mode`, `customScripts`, `configuration`) | Implemented | Scripts run in Node.js 22.13 or later (D-0022); guide: `docs/custom-db.md`. `login`, `get_user`, `create` and `change_password` are called by hosted login, the password grants, `/dbconnections/*` and the reset flow. `verify` runs when a verification ticket is opened, `delete` when a user is deleted through the Management API and `change_email` when its email changes (D-0043). Error responses: D-0023. Profiles: D-0024. Verified with auth0/legacy 7.4.0, @auth0/auth0-auth-js 1.16.1 and Chromium (m9) |
| Consent and user grants (`/u/consent`, `prompt=consent`, `use_scope_descriptions_for_consent`, `skip_consent_for_verifiable_first_party_clients`) | Implemented | Guide: `docs/consent.md`. Decisions D-0025 to D-0027. Verified with express-openid-connect 3.4.0 and Chromium (m10). A grant is stored only when the user accepts a consent screen (D-0026); no grants API until sub-project 3 |
| Third-party applications: `strict` and `permissive` modes | Implemented | Strict verified by raw HTTP plus express-jwt 8.5.1 and jwks-rsa 4.1.0 (m10); permissive verified with express-openid-connect 3.4.0. Permissive behaviour follows Auth0's documentation because the maintainer's tenant cannot create permissive clients (D-0025) |
| API access policies (`subject_type_authorization`, client grant `subject_type`) | Implemented | `deny_all` verified with node-auth0 (password grant refused, m3); the other policies, scope capping and refresh re-checks are covered by server tests only. Client credentials always need a client grant (Auth0 offers no `allow_all` for clients) |
| Confirmation prompt for non-verifiable callbacks and `prompt=none` limits | Implemented | Verified with auth0-spa-js 2.28.3 (m10). Tenant and client `skip_non_verifiable_callback_uri_confirmation_prompt`; `consent_required` for `prompt=none` (D-0027) |
| `redirection_policy` (`open_redirect_protection`, `allow_always`) | Implemented | Decline error page verified in Chromium (m10); `allow_always` redirects are covered by server tests only (D-0027) |
| Domain connections (`is_domain_connection`) | Implemented | Third-party clients log in only through them; covered by server tests (and used by the m10 E2E tenant). `/dbconnections/*` still checks `enabled_clients` only |
| Storage drivers: memory, SQLite, PostgreSQL 14+, MySQL 8.0.17+ | Implemented | All pass `pkg/storetest` (SQLite in every test run; PostgreSQL 17 and MySQL 8.4 via `make test-sql` and CI); E2E runs on SQLite |
| `POST /oauth/par` | Implemented | First-party confidential clients with client-secret authentication; guide: `docs/par.md`. Decision D-0028. Verified with express-openid-connect 3.4.0, @auth0/nextjs-auth0 4.32.0 and @auth0/auth0-auth-js 1.16.1 (`pushedAuthorizationRequests: true`). `response_type=token` is `501`, and `response_mode`/`prompt` are checked at PAR (differences from Auth0). `private_key_jwt`, mTLS, JAR and RAR are not supported |
| `request_uri` at `/authorize` | Implemented | From PAR only; replaces every other parameter except `client_id`; failures are error pages (D-0029). Strict third-party clients still refuse it (D-0025) |
| Client `require_pushed_authorization_requests` and tenant `pushed_authorization_requests_supported` | Implemented | A plain `/authorize` from a requiring client redirects with `invalid_request`; the seed refuses the client setting without the tenant setting, on public clients and on third-party clients (D-0029, D-0030) |
| Discovery: `pushed_authorization_request_endpoint`, `request_uri_parameter_supported` | Implemented | The endpoint appears only while the tenant setting is on; `request_uri_parameter_supported` is always `false` (D-0030) |
| `POST /oauth/device/code` | Implemented | RFC 8628 for first-party native clients without a secret; guide: `docs/device-flow.md`. Decision D-0031. Verified with Auth0.AuthenticationApi (auth0.net) 7.49.0 and Chromium (m10-device). Form or JSON body; 15-minute codes, 5-second interval |
| Grant `urn:ietf:params:oauth:grant-type:device_code` | Implemented | `authorization_pending`, `slow_down` (polls under 1 s apart), `access_denied` and `expired_token` as `403`/`429` per observation; tokens once; refresh tokens rotate and revoke as usual; no `sid` in the ID token (D-0031) |
| Tenant `device_flow` (`charset`, `mask`) | Implemented | `base20` or `digits`; seed refuses invalid masks and device grants on non-native, secret-holding or third-party clients (D-0033). Management API access planned (sub-project 3) |
| Device screens: `/activate`, `/device/confirmation`, `/device/success`, `/device/denied` | Implemented | Entry, confirmation (always shown), success and denied pages with the four `device-code-*` custom text prompts; login and consent reuse `/u/login` and `/u/consent` (D-0032). Activation limits are zeroauthy's own numbers (D-0034) |
| Discovery: `device_authorization_endpoint` | Implemented | Advertised with the device grant in `grant_types_supported` (D-0033) |
| Implicit/hybrid flows | Planned | Not part of Plan 5 |
| Passwordless, MFA, social connections, Actions | Planned (sub-project 2) | |
| Management API v2: authentication (machine-to-machine tokens for the canonical `https://<tenant>/api/v2/` audience, operator tokens), errors, pagination, `fields` | Implemented | Guide: `docs/management-api.md`. Decisions D-0038 to D-0040 |
| Management API v2: `/api/v2/clients` (list, create, get, update, delete, `rotate-secret`) | Implemented | Verified with auth0-cli 1.37.0 (m13-mgmt-cli: `apps create/list/show/update/delete`, `api get clients`) and a contract test against `api/management.yaml`. Secrets encrypted and revealed with `read:client_keys` (D-0038); defaults and differences in D-0039 |
| Management API v2: `/api/v2/resource-servers` (list, create, get by ID or identifier, update, delete) | Implemented | Verified with auth0-cli 1.37.0 (m14-mgmt-cli: `apis create/list/show/update/delete/scopes list`) and the console (m14-console); contract test against `api/management.yaml`. Decision D-0041. Differences from Auth0: `RS256` only (`HS256`, `PS256` and `signing_secret` refused); `token_lifetime_for_web` stored but unused; `enforce_policies` only `false`, `token_dialect` only `access_token`, `consent_policy`, `proof_of_possession`, `token_encryption` only null; system APIs can be read and granted, never deleted, and only some settings change; the system API is named "zeroauthy Management API" |
| Management API v2: `/api/v2/client-grants` (list, create, get, update, delete) | Implemented | Verified with auth0-cli 1.37.0 (`client-grants create/show/list`, `api` verbs) and the console. Decision D-0041. Differences: scopes the API does not define are refused on create as well as update; grants to a Management API only for the tenant's own identifier and its scopes; `organization_usage`, `allow_any_organization`, `authorization_details_types` and `default_for` accept only inert values; checkpoint paging (`from`/`take`) is supported, the `allow_any_organization` and `default_for` list filters are not |
| Management API v2: `/api/v2/connections` (list, create, get, update, delete) and `/connections/{id}/clients` | Implemented | Database connections (strategy `auth0`) only. Verified with auth0-cli 1.37.0 (m15-mgmt-cli: `connections create/list/show/update/delete`, `enabled-clients show/update`, sign-ups with refused and accepted passwords) and the console (m15-console); contract test against `api/management.yaml`. Decision D-0042; observations in `docs/compat/observations/management-connections.md`. Enforced: password complexity, history, dictionary (`en_10k`, `en_100k`, custom words), personal data, username limits, brute-force gating. Stored, not enforced: `authentication_methods`, `passkey_options`, `attributes`, `precedence`, `mfa`, `non_persistent_attrs`, `metadata`, `connected_accounts`, `never_on_login` and others (listed in D-0042). Differences: other strategies refused; script size limit is zeroauthy's; legacy `min_length` above 72 refused; history, dictionary and personal-data runtime behaviour was not observable on Auth0 and is zeroauthy's own |
| Operator-only script try (`POST /api/system/tenants/{tenant}/connections/{id}/scripts/{name}/try`) | Implemented | zeroauthy extension, not an Auth0 surface. Configuration values are masked in its response and in the server log (D-0042) |
| Management API v2: `/api/v2/users` (list and v3 search, create, get, update, delete) and `/api/v2/users-by-email` | Implemented | Verified with auth0-cli 1.37.0, node-auth0 and the console (m17); contract test against `api/management.yaml`. Decision D-0043; query guide `docs/user-search.md`; observations in `docs/compat/observations/management-users.md`. Differences: search is immediately consistent; default picture uses Gravatar `d=mp`; `device.*_asn` not returned; `blocked: false` is never shown; `search_engine=v1` refused |
| Management API v2: `/api/v2/users/{id}/identities` (link, unlink) | Implemented | By `provider`/`user_id` or `link_with` (an ID token of the calling client). Unlink recreates the secondary from `profileData` only (D-0043) |
| Management API v2: `/api/v2/users/{id}/sessions`, `/api/v2/sessions/{id}` | Implemented | Checkpoint paging only; deletes are `202`; deleting sessions leaves refresh tokens alone (D-0043) |
| Management API v2: `/api/v2/users/{id}/refresh-tokens`, `/api/v2/refresh-tokens/{id}` | Implemented | zeroauthy ID formats (no `dcr_` prefix); deleting one revokes its rotation family (D-0043) |
| Management API v2: `/api/v2/grants` (list, delete by user, delete by ID) | Implemented | `clientID` (sic) and a sorted `scope` array, as Auth0 returns them (D-0043) |
| Management API v2: `/api/v2/tickets/password-change`, `/api/v2/tickets/email-verification` | Implemented | Hosted pages `/u/reset-verify` and `/u/email-verification`; the verification email is sent at sign-up and user creation. Success page of a password-change ticket does not redirect to `result_url`, as on Auth0 (D-0043) |
| Management API v2: jobs (user import, user export, verification email) | Planned (Plan 18) | |
| Management API v2: other resources (tenant settings, …) | Planned (sub-project 3, slices 5–6) | |
| Admin console (`/admin` on the system host) and system API (`/api/system/tenants`, `/api/system/operators`) | Implemented | zeroauthy extension, not an Auth0 surface. Guide: `docs/console.md`; D-0040. Verified in Chromium (m13-console) |
| SAML, WS-Federation | Planned (sub-project 4) | |
| Deprecated endpoints (`/oauth/ro`, `/delegation`, `/tokeninfo`, `/oauth/access_token`, impersonation) | Not planned | Deprecated by Auth0 |
| Hosted page languages (`ui_locales`, `Accept-Language`, `enabled_locales`, per-tenant `custom_text`) | Implemented | English catalog only; verified with @auth0/auth0-spa-js 2.28.3 (`ui_locales`) and browser `Accept-Language`; custom-text Management API planned (sub-project 3) |
| Storage plugins (`plugin://` DSN, gRPC) | Implemented | zeroauthy extension, not an Auth0 surface; Go SDK in `pkg/storeplugin`; see D-0021 |
